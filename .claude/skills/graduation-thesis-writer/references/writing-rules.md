# 论文写作规则

## 1. 真实性约束
- 只能依据当前项目代码、页面、接口、数据库模型与已验证流程写作。
- 若功能只是部分具备，应写为“部分实现”或“后端已支持、前端待完善”。
- 不可把未实现模块写成已完成成果。

## 2. 长文分批策略
- 优先写入文件，不要把整章长文堆在对话中。
- 若用户要求整篇论文，默认分阶段输出：
  1. 大纲
  2. 绪论
  3. 需求分析
  4. 系统设计
  5. 系统实现
  6. 系统测试
  7. 总结与展望
- 每完成一章，更新对应 Markdown 文件。

## 3. 占位提示规范
统一使用全角中文括号，示例：
- `（此处放置首页原型图）`
- `（此处放置登录页界面图）`
- `（此处放置订单详情页界面图）`
- `（此处放置管理后台工作台界面图）`
- `（此处放置数据库 E-R 图）`
- `（此处可将 mermaid 转为图片插入论文）`

## 4. UML / 流程图规范
- 优先用 mermaid 代码块。
- 在图前或图后写：`（此处可将 mermaid 转为图片插入论文）`
- 适合输出的图：
  - 系统总体架构图
  - 业务流程图
  - 用例图
  - 时序图
  - 数据库关系图

## 5. 润色规则
- 保持事实不变。
- 优先修正：
  - 学术表达不规范
  - 语句重复
  - 段落衔接弱
  - 术语不统一
- 不得通过润色改变功能真实边界。

## 6. 文件维护规则
- 默认维护以下文件：
  - `00-论文大纲.md`
  - `01-绪论.md`
  - `02-需求分析.md`
  - `03-系统设计.md`
  - `04-系统实现.md`
  - `05-系统测试.md`
  - `06-总结与展望.md`
  - `README.md`
- 若用户要求摘要、致谢、参考文献、附录，再新增对应文件。

## 7. 推荐回复格式
每次完成后，用简洁说明告诉用户：
- 已更新哪些文件
- 哪些位置加了图片/UML 占位
- 下一步建议继续补写哪章
